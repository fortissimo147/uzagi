対象: `lovewcycle.com/games/others/typhoon-escape.html` の再現版。

ゲーム内の文言はすべて英語にする。

## 0. 前提

### 0.1 元ゲームの仕様は入手済み **[確認済]**

`https://lovewcycle.com/games/others/typhoon-escape.html` への直接取得は本セッションの

| 項目 | 値 | 確認方法 |

### 0.3 設計の中心方針 — ルール層と世界層の分離

ルールは確定したが、**平面 → 球面の移植で最も壊れやすいのは「ルールが座標系を直接触る」構造**である。
元ゲームは `jp.x += vx * sp * dt` のように px 座標を直接いじっており、これをそのまま持ち込むと
球面化で全滅する。依存を一方向に固定し、ルールは「面(Surface)」の抽象だけを触る。

```
rules/   ← 勝敗・スコア・スポーン・難度曲線（元ゲームの定数をそのまま持つ層）
   ↓ 依存
world/   ← 球面座標・大圏移動・台風の運動・地図データ（座標系の詳細を隠す層）
   ↓ 依存
render/  ← three.js の描画とカメラ（ゲーム内容を一切知らない）
```

`rules/` は `world/` の API（`Surface`, `Storm`, `Body`）だけを触る。
`world/` は `rules/` を import しない。この向きを `npm test` の静的チェックで守る。

## 1. 元ゲームの実仕様 **[確認済: 元ソース読解]**

以下はすべて元 `<script>` からの直接引用・実測値。**推測は含まない。**

### 1.1 基本構造

- 論理ビューポート `W=400, H=700`、基準寸法 `M=700`。実画面へは `SC = min(VW/W, VH/H)` でレターボックス。
- 投影は**メルカトル**。`CEN=170, LONW=110, LATN=75, LATS=-60`。
  `px(lon) = W/2 + (wrap(lon)-CEN)·W/LONW` / `py(lat) = (MY-merc(lat))/(MY-MN)·H`。
  → 画面 x∈[0,400] は **経度 115°E–225°E**（＝135°W）に対応。1° 経度 = 3.6364 px **[確認済: 計算]**
- プレイヤーは**日本列島そのもの**。`jp = {x, y}` を動かす。列島のリングは `jp` からの相対座標で
  `K=1.6` 倍に拡大して保持（`buildMap()` で `px(138), py(37)` を原点に正規化）。
- **開始位置は `px(144), py(37)`** — つまり形状の基準経度(138)より東に 6° ずれた位置から始まる。
- `jp.x` は `[30, 370]`、`jp.y` は `[30, 670]` にクランプ。**プレイヤーはビューポートの外へ出られない。**

### 1.2 ゲームループとスコア

| 項目 | 実仕様 |
| --- | --- |
| dt | `min(0.05, (now-last)/1000)` — 1フレーム最大 50 ms |
| 時間 | `elapsed += dt` |
| 暦 | `START = new Date(2026,7,1)` = **2026-08-01**、`gameDate()` は `START + floor(elapsed)` **日** |
| **時間スケール** | **実時間 1 秒 = ゲーム内 1 日** |
| スコア | **生存日数** `Math.floor(elapsed)` |
| 敗北 | **接触即死**（1回でも当たれば終了） |
| クリア条件 | **なし。エンドレス。** |
| 敗北演出 | `over` 後 `dt *= 0.3` のスローモーションを 1500 ms、その後ポップアップ |

### 1.3 当たり判定 **[設計上もっとも重要]**

```js
for (i of ty) for (j of jpPts)
  if (Math.hypot(jp.x + jpPts[j][0] - ty[i].x, jp.y + jpPts[j][1] - ty[i].y) < ty[i].r * 0.55)
```

- 判定対象は**海岸線の全頂点**（日本110mで 65 点）。塗りの内側は判定しない。
- 致死半径は**外側の黄色い円 `r` ではなく、内側の赤い円 `r × 0.55`**。
- 上陸地域は、**当たった頂点の元の経緯度** `jpPts[j][2], jpPts[j][3]` を `region()` に渡して決める。

### 1.4 台風の運動 — 5つの進路パターン

`spawn()` が毎回このうち1つを等確率で選ぶ。

| name | segMin | segMax | jitter | pull | spd | stall | bias |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 直進 | 4 | 7 | 0.3 | 0.2 | 1.2 | 0 | — |
| 迷走 | 0.7 | 1.6 | 2.4 | 0.2 | 0.9 | 0 | — |
| 転向 | 1.5 | 3 | 0.3 | 0.2 | 1.0 | 0 | `±(0.5–1.0)` 発生時に固定 |
| 追尾 | 1.5 | 3 | 0.6 | 0.9 | 0.8 | 0 | — |
| 停滞 | 1.5 | 3 | 1.0 | 0.4 | 1.3 | 0.5 | — |

`timer` が尽きるたびに1回だけ進路を更新する（毎フレームではない）:

```js
d = wrapAngle(toward(player) - t.ang);
t.ang += d * pat.pull + (Math.random() - 0.5) * pat.jitter + (pat.bias || 0);
t.timer = segMin + rand*(segMax - segMin);
t.trail.push([t.x, t.y]);
```

- `pull` が**プレイヤー追尾の強さ**、`jitter` が**ランダム偏向**、`bias` が**一方向への転向癖**。
- `stall > 0` のパターンは、進路更新時に確率 `stall` で「停滞」へ入り（`timer = 1–2.5 s`）、
  速度が `tsp * 0.15` に落ちる。次の更新で必ず解除。
- 個体差 `t.spd = pat.spd * (0.8 + rand*0.4)`。
- 発生直後の向きは `toward(player) + (rand-0.5)*0.8` — **必ずプレイヤー方向を向いて生まれる。**

### 1.5 台風の強度と寿命

| 変数 | 実仕様 |
| --- | --- |
| 初期半径 | `r = M*0.015 = 10.5 px` |
| ピーク半径 | `rPeak = M*0.05 + rand*M*0.035` = **35–59.5 px** |
| 発達時間 | `growT = 3 + rand*3` 秒（＝ゲーム内 3–6 日） |
| 発達 | `r += rPeak/growT * dt`（`rPeak` で頭打ち） |
| 衰弱開始 | ピーク到達後、毎フレーム確率 `dt * 0.06`（≒ 期待値 16.7 秒） |
| 衰弱 | `r -= rPeak*0.12 * dt` |
| 寿命 | `life = 12 + rand*10` 秒。**残り 5 秒を切ると強制衰弱** |
| 消滅 | `r <= M*0.012 (=8.4 px)` または `life <= 0` → 「温帯低気圧に変わりました」 |
| 画面外消滅 | 一度画面内に入った後に `r` 分はみ出す、または常に ±150 px 超 → 「遠ざかり、消滅しました」 |

### 1.6 速度と難度曲線 **[確認済: 計算]**

| 項目 | 式 | 値 |
| --- | --- | --- |
| プレイヤー速度 | `M*0.125` | 87.5 px/s（一定） |
| 台風基準速度 | `tsp = M*0.09 + elapsed*M*0.0035` | t=0 で 63 px/s、**毎ゲーム内日 +2.45 px/s** |
| 実速度 | `tsp * t.spd`（停滞中は `tsp * 0.15`） | |
| **速度逆転** | `0.125 = 0.09 + 0.0035·t` | **t = 10.0 ゲーム内日で台風がプレイヤーより速くなる** |
| 発生間隔 | `max(1.5, 4 - elapsed*0.08)` | 4 s → **t = 31.25 日で下限 1.5 s** |
| 同時数上限 | 7 | |
| 発生位置 | 4辺のいずれか、画面外 60 px | |

**この「10日で追い越される」設計が本作の核**である。逃げ切りは不可能で、
プレイヤーにできるのは「かわす」ことだけ。だから生存日数がスコアになる。

### 1.7 予報円（進路予想）の描画

`setForecast()` が `timer` 更新時に再計算する。

```
v  = 停滞中 ? tsp*0.15 : tsp*t.spd
T  = t.timer                        // 次の進路更新までの残り時間
r  = 衰弱中/残5秒以内 ? r - rPeak*0.12*T : min(rPeak, r + rPeak/growT*T)
(fx, fy) = 現在位置 + 現在の向き × v × T
fr = max(M*0.012, r) * 0.55         // 予報円の半径＝将来の致死半径
```

描画は 4 要素: 中心への破線、`fr*0.5` の破線円、`fr` の赤い実線円、
`len > fr - r*0.55` のとき現在の致死円と予報円の**共通外接線 2 本**。
過去進路は白の実線ポリライン＋各節点に半径 2.5 の点。

**つまり予報円は「次の進路更新までは確実にこう動く」という正直な情報**であり、
プレイヤーはこれを読んで回避する。ここがゲーム性の中心なので、球面化でも厳密に維持する。

### 1.8 大陸を押しのける機構

```js
pushLand(dt):  各 body について、jp が AABB±120px 内なら
               日本の全頂点で outer リングに対する ray-casting 判定、
               内側にある頂点の相対座標を合計 (sx,sy) し、
               B.v = normalize(sx,sy) * M*0.125
slideLand(dt): B.o += B.v*dt;  B.v *= Math.pow(0.12, dt);  |B.v|<0.5 で停止
```

- 押す向きは**日本の中心から見た貫入点の方向**。＝ 大陸は日本から押しのけられる。
- `land-110m` の各ポリゴンが body。**南極大陸だけ除外**（`maxLat < -55`）。
  この除外は `bodies.push` の手前にあるので、**元ゲームは南極を押せないのではなく、そもそも描いていない** **[確認済]**。
  メルカトルの下端（`LATS=-60`）で南極が横一杯に引き伸ばされるのを避けるための措置。
- **元ゲームは `land` から日本を抜いてある** **[確認済]**: 素の `land-110m` は 125 ポリゴンだが
  埋め込みデータは 121 ポリゴンで、本州中央 (138.5°E, 36.5°N) を含む陸ポリゴンが 0 個。
  自国の「影」が地図に残らないようにしてある。本作も台湾本島に対して同じ処理が要る（§3.3）。
- 減衰係数 `0.12^dt` はフレームレート非依存。押した後も慣性で滑る。

## 1b. 日本 → 台湾・平面 → 球面の変換 **[確認済: Nodeで実測・検算]**

### 1b.1 何を保存し、何を変えるか

元ゲームの手触りを決めているのは**絶対値ではなく比**である。
以下の 3 つの無次元比を**厳密に保存**し、それ以外（画面px・投影）を捨てる。

| 保存する比 | 元の値 |
| --- | --- |
| 致死半径(ピーク最大) / 自国の外接半径 | 0.466821 |
| プレイヤー速度 / 自国の外接半径 [/s] | 1.248185 |
| プレイ窓の幅 / 自国の外接半径 | 5.705988 |

### 1b.2 換算定数の導出

**プレイヤー本体は台湾本島のみ**（澎湖・金門・馬祖・蘭嶼・緑島は含めない。ユーザー指定）。
`countries-10m` の台湾ジオメトリのうち**最大リング（404頂点）**がそれにあたる。

**描画倍率は `K_TW = 1.0`（実寸）** — ユーザー選択。
元ゲームは日本を `K = 1.6` 倍に誇張して描いていたが、本作は台湾本島を
**他の陸と同じ縮尺で**描く。地球儀として正しくなる。

> **注意（重要）**: `K_TW` は難度のつまみでは**ない**。
> 台風の半径も速度もプレイ窓もすべて §1b.1 の比を通じて自国サイズに連動するので、
> `K_TW` を変えても**難度は一切変わらない**。変わるのは「1° が何 km か」＝
> 世界全体の絶対スケールと、カメラの寄り具合だけである。
> `ORIG.K = 1.6` は元ゲームの事実なので固定。`K_TW` だけが本作の設計選択。

> **外接角半径の測り方**: リング末尾の閉じ点（先頭と同一座標の重複）を**必ず落としてから**
> 球面重心を取る。残すとその頂点が二重に重みを持ち、日本 110m で 9.6226° → 9.5015° と
> **1.3% 小さく出る**。`bake-geo.mjs` が焼く頂点列も閉じ点なしなので、そちらに合わせる。

実測値 **[確認済: `tools/calibrate.mjs`]**:

| 量 | 値 |
| --- | --- |
| 日本（110m 全島・62 頂点）の真の外接角半径 | 9.6226° = 1070.0 km |
| **台湾本島（10m・403 頂点）の真の外接角半径** | **1.8577° = 206.6 km** |
| 日本の最大大圏スパン | 17.6183° |
| 台湾本島の最大大圏スパン | 3.4465° = 383.2 km |
| **サイズ比 日本/台湾本島** | 外接半径 **5.1797 倍** / スパン 5.1120 倍（1.3%以内で一致） |
| 元マップの弧長スケール @lat37 | `(400/110)/cos37° = 4.5532 px/°` |
| 元ゲームでの日本の描画外接半径 | `9.6226 × 4.5532 × 1.6 = 70.10 px` |
| 本作での台湾本島の描画外接角半径 | `1.8577 × 1.0 = 1.8577°` = 206.6 km |

したがって換算定数は

```
A = 1.8577° / 70.10 px = 0.026501 度(弧長) / 元px
```

### 1b.4 球面化で置き換えが必要な 5 箇所

| 元の機構 | 平面前提 | 球面での置き換え |
| --- | --- | --- |

## 2. 座標系と球面数学（**確定** / 検算済）

### 2.1 単位と変換 **[確認済: Nodeで往復検算]**

すべての位置は `{lat, lon}`（度）で持ち、描画直前に単位ベクトルへ落とす。

```
lat = φ, lon = λ （ラジアン）
x =  cos φ · sin λ
y =  sin φ
z =  cos φ · cos λ        // 経度0が +Z を向く。北極が +Y。
```

逆変換 `lat = asin(y)`, `lon = atan2(x, z)`。
台北 (25.0330, 121.5654) の往復で誤差 0（倍精度で 25.033000 / 121.565400 に復帰）。

### 2.2 距離

球面上の2点間は `d = R · acos(clamp(a·b, -1, 1))`、`R = 6371.0088 km`（IUGG 平均半径）。
検算値 **[確認済]**:

| 区間 | 本設計の計算値 |
| --- | --- |
| 台北 → 高雄 | 296.8 km |
| 台北 → マニラ | 1161.7 km |
| 台北 → グアム | 2751.5 km |

**注意**: 距離の計算そのものは検算済だが、**都市の座標は記憶に依るもの** **[推定]**。
実装時に地名を出すなら座標の出典を明記する。ゲーム内では地名を使わないので影響はない。

### 2.3 移動 — 大圏上の厳密ステップ（**設計の要**）

「緯度経度に直接足す」方式は高緯度で速度が狂い、極で破綻する。採らない。
位置 `p`（単位ベクトル）と進行方向 `t`（`p` に直交する単位接ベクトル）を組で持ち、
角度 `θ = v·dt / R` だけ回す:

```
p' = p·cos θ + t·sin θ
t' = -p·sin θ + t·cos θ
```

この形は正規直交性を保つので、緯度によらず速度が一定になり、極も普通に通過できる。
浮動小数の蓄積誤差だけ毎フレーム再正規化する（`t -= p(p·t)`, then normalize）。

旋回は `t` を `p` 軸まわりに回すだけ:  `t' = rotateAround(t, p, ω·dt)`。

台風の進路も同じ機構で表現する（進路の曲がり＝`ω` の時間変化）。

### 3.3b 南極大陸の扱い — **極に穴を開けない** **[確認済: 実測]**

南極ポリゴンについて機械的に確認した（`land-110m` / `50m` / `10m` すべてで同じ結論）:

- **経度の巻き数が 1.0000** — このリングは**南極点を 1 周囲んでいる**。
- 最南端は **-85.222°**（10m）。南極点まで **4.778° = 531 km** 届いていない。

したがって**経緯度をそのまま三角形分割すると南極点に半径 531 km の穴が開く**。

**扇形分割は駄目だった** **[確認済: 実装して面積で検算]**。
当初この設計書は「極を扇の中心にする」と書いていたが、実装して測ったら**面積が 2.39 倍**になった。
南極の海岸線は極から見て**星形でない**（フィヨルドがある）ため、扇の三角形が海側へはみ出して重なる。

正しい手当ては「**極で切り開く**」こと。経度を巻き戻したリングの末尾に
「極まで降りる → 反対端へ戻る」2 点を足すと、平面上の単純多角形になる。
足した 2 点はどちらも 3D では極そのものに写るので、余分な面は生まれない。
これで面積比 **1.002**。

巻き数 0 のリングは、経度を巻き戻してから経緯度平面でそのまま earcut にかける。
心射方位図法は使わない。ユーラシアのように 90 度を超えて広がるポリゴンで破綻するため。

### 3.3b-2 長い三角形の細分 **[確認済: 面積で検算]**

earcut は経緯度平面で分割するので、遠く離れた頂点を結ぶ**長い三角形**が出る。
そのまま球面に貼ると平らな三角形が球の内側へ沈み込み、陸に穴が空く。
実測で**最長弦 1.037（弧 60 度）・沈み込み 924 km**。

対策は辺の中点での細分。ただし単純に割ると **T 字接合**ができてひび割れる。
辺の中点を共有キャッシュで管理し、**印のついた辺を持つ三角形をまとめて割る**
（red-green 細分の簡易版。1 辺→2 枚、2 辺→3 枚、3 辺→4 枚）。

- 判定は**球面上の実際の弦長**で行う。経緯度平面の距離だと極の近くで割りすぎ／割らなさすぎになる。
- しきい値 **弧 1 度**。沈み込み 0.24 km で、最寄りズーム 1.29 km/px でもサブピクセル。
- 結果: **741,868 三角形 / 578,439 頂点**、生成 **1.4 秒**（Node 実測）。
  位置 6.6 MiB + index 8.5 MiB で GPU 的には軽い。

**検算方法**: 分割結果の立体角合計を、Chamberlain–Duquette の球面多角形面積公式
（分割とは独立の計算）と突き合わせる。全 4,013 ポリゴンで **0.5% 以内**、最悪 0.40%。
陸地の総面積は地球表面の **28.8%（146.7 百万 km²）** になった。
極冠と赤道の矩形については解析解とも突き合わせてある。

押しのけ判定（点の内外判定）も同様に極を意識する必要がある。
§3.3c の子午線レイキャストは、極を囲むリングに対してもそのまま正しく動く。

### 3.3c 押しのけ判定の計算量 — 経度バケット索引

元ゲームは `land-110m`（最大リング 1,000点規模）× 日本 65 点で済んでいたが、
本作は `land-10m`（**最大リングは 83,725 点**）× 台湾 404 点になる。素朴に回すと重い。

**子午線レイキャスト＋経度バケット**で解く:

- 内外判定は「テスト点の経度 λ で子午線に沿ってレイを飛ばし、リングの辺との交差数を数える」。
- したがって**辺を経度で 720 個（0.5°刻み）のバケットに振り分けて**おけば、
  1 回の判定で見る辺は 1 バケット分だけになる。
- 索引はロード時に O(頂点数) で構築する。焼き込みデータには含めない。
- 極を囲むリング・日付変更線をまたぐ辺も、経度の最短弧で判定すれば正しく扱える。

**実測にもとづく見積り** **[確認済: 頂点数の実測 / 演算数は計算]**:
最大の陸（アフロ・ユーラシア）83,725 辺 ÷ 720 バケット ≒ **116 辺/バケット**。
404 点 × 116 = 約 47,000 回/フレーム。60fps でも 2.8M 回/秒で、JS で余裕。
AABB 早期棄却があるので実際に見る body は毎フレーム 1〜3 個。元ゲームと同じ計算量帯に戻る。

### 3.4 パイプライン

```
npm run bake:geo
  → tools/bake-geo.mjs
      node_modules/world-atlas/{land-10m,countries-10m}.json を topojson-client でデコード
      → 台湾本島（最大リング）を抽出して player 層へ
      → land から自国ポリゴン 1 個を除去（球面重心の内外判定で特定）
      → 極を囲むリングに巻き数フラグを立てる（§3.3b）
      → 量子化 → リング内差分符号化 → Int16Array → Base64
      → src/data/geo.js を生成（Base64 文字列 + リングオフセット表 + 巻き数フラグ）
```

生成物 `src/data/geo.js` は **リポジトリにコミットする**。
理由: 実行時・ビルド時ともにネットワーク不要にし、1ファイル完結版を成立させるため。
（既存リポジトリの `voicebank.js` と同じ「生成物をコミットし、手で編集しない」方式に合わせる。）

1. **海** — `IcosahedronGeometry(R, 5)` に `#1B2F5E`。緯度方向に淡いグラデーション。
   背景（球の外）は `#0E1A36`。
2. **他の陸の塗り** — `land` データ（**南極大陸を含む全ポリゴン**）を球面三角形分割する。
   `#4E6656` 塗り、`#7C9A86` の輪郭線。**body ごとに別 Mesh** にし、
   押しのけの回転クォータニオンを `Object3D.quaternion` に直接入れる（§1b.4）。
   三角形分割は §3.3b / §3.3b-2 の通り（極を囲むリングは極で切り開く → earcut → 弧 1 度で細分）。
   日付変更線の継ぎ目処理（元ゲームの `Math.abs(lon-prev) > 180` 分岐）は
   **球面では不要**。頂点を 3D で持てば継ぎ目そのものが存在しない。
3. **自国（台湾）の塗り** — `player` データを同様に。`#8FBF7F` 塗り、白 `#FFFFFF` の輪郭。
   `K_TW = 1.0`（実寸）なので拡大処理は入れず、元の経緯度のまま焼く。
   こちらも独立した `Object3D` で、位置クォータニオンだけを毎フレーム更新する。
4. **海岸線（線）** — 塗りと同じデータを `THREE.LineSegments` で半径 `R×1.0005` に重ねる。
   ベクタなので**ズームに対して常に鮮鋭**。塗りのテッセレーション誤差を線が隠す。

### 4.1b ドローコール — 押された陸だけを切り出す

素朴に「body ごとに 1 Mesh」にすると **4,060 ドローコール**になり 60fps が出ない。
しかし**押されていない陸はすべて同じ変換（恒等）**なので、まとめて 1 つにできる。

- 起動時: 全 body の三角形を**1 本のマージ済み `BufferGeometry`** に詰め、
  body ごとの index 範囲を覚えておく。→ **ドローコール 1**
- ある body が**初めて押された瞬間**に、その index 範囲をマージ済み index buffer から
  取り除き（末尾を詰めるだけ、O(n) 1 回）、独立した `Mesh` として作り直す。
- 以降その body だけが自分のクォータニオンで動く。

1 回のプレイでプレイヤーが実際に押せる陸はせいぜい数個なので、
**ドローコールは 1 + （押した数）** に収まる。海岸線の `LineSegments` も同じ方式。

### 4.2 大気

`BackSide` の球を一回り大きく重ね、視線と法線の内積によるフレネル項で加算合成。
シェーダ数行で済み、画像もポストプロセスも不要。

### 4.3 台風の見た目 — **見た目と判定を一致させる**

元ゲームの描画要素を球面へ 1:1 で移す。ここは省略しない。ゲーム性の中心だから（§1.7）。

| 要素 | 元 | 球面での実装 |
| --- | --- | --- |
| 外円（黄 `#FFE000`, 塗り50%） | `arc(x,y,r)` | 地表に張り付く角半径 `r` の小円リング |
| **内円（赤 `#E61E2D`, 塗り75%）＝当たり判定** | `arc(x,y,r*0.55)` | 同、角半径 `0.55r`。**判定と完全に同一の値を描く** |
| 中心の白い × | 2本の線 | 中心にビルボードの × |
| 過去進路 | 白実線 + 節点の点 | 節点を大圏で結んだ `Line` + 各節点に小円 |
| 予報の破線 | `setLineDash([5,4])` | 大圏に沿った破線ジオメトリ（線分を等間隔に間引く） |
| 予報円 `fr` | 赤い実線円 | 角半径 `fr` の小円 |
| 予報円 `fr*0.5` | 白い破線円 | 同 |
| 共通外接線 2 本 | `acos((rs-rw)/len)` | **接平面で同じ式を解いてから球面へ写す**。局所現象なので歪みは無視できる |

### 4.3b 渦の実装 **[確認済: 実装して実ブラウザで確認]**

接平面の極座標で対数螺旋 `ρ(φ) = eye·e^(b·φ)` を引き、各サンプルで幅ぶん膨らませて
帯（三角形ストリップ）にし、`v = c·cosρ + (north·cosφ + east·sinφ)·sinρ` で球面へ写す。

| 定数 | 値 | |
| --- | --- | --- |
| `ARMS` | 5 | 腕の本数 |
| `SPIRAL_B` | 0.26 | 巻きの強さ |
| `EYE` | 0.13 | 眼の半径 / 外側半径 |
| `SPIN` | 2π/6 rad/s | **6 秒で 1 回転**。北半球は反時計回り、南半球は時計回り |

腕は太さの違う 2 層（幅 2.1 倍・不透明度 0.20 / 幅 0.85 倍・不透明度 0.62）を重ねて雲らしくする。

**描く順が肝**（下から）: 雲の傘 → 外円の淡い塗り → 内円の塗り → **渦の腕** → 眼 → 境界の帯 → 線。
最初は渦を塗りの**下**に敷いたが、赤い塗り（当時 0.75）に埋もれて「赤い塊」にしか見えなかった。
渦を上に出し、内円の塗りを 0.30 に落とすことで渦が主役になる。

**当たり判定の境界は「線」ではなく「帯」で描く**。WebGL では `LineBasicMaterial` の
`linewidth` が常に 1px 扱いになり、寄ったときに致死圏の境界が読めなくなる。
半径の 4.5% 幅の円環メッシュを重ね、遠景用に 1px の線も併せて置く。

`test/play.test.mjs` が**赤い帯の外縁の角半径が `r × 0.55` と 1e-3 度以内で一致する**ことを
実ブラウザで検査する。**渦は装飾**であり、判定は内円だけが持つ、という約束の担保。

台風が画面外にいる間は、画面端に方位インジケータを出す（元にはない。球面では
「画面外」が常態になりうるので追加が必要）。

## 5. カメラ（**確定** — 「動く時に適宜画面を動かす」要件の実装）

### 5.1 追従フレーム — **北を上に固定する**

元ゲームは常に北が上のメルカトルであり、プレイヤーの向きという概念がない
（`vx,vy` は速度そのもの。§1.9）。この性質は**そのまま維持する**。

したがってカメラは「プレイヤーの進行方向」を追わない。追うのは**位置だけ**:

```
up      = 台湾の中心 p の地表法線（＝ p 自身）
north   = 正規化( ŷ - p(p·ŷ) )      // 北極方向を接平面へ射影
right   = north × p
```

この (right, north, p) から目標クォータニオンを作り、
`slerp(current, target, 1 - exp(-k·dt))` で追従する。
`exp` 形にするのはフレームレート非依存にするため（`lerp(a,b,k·dt)` は可変fpsで挙動が変わる）。

**極付近**では `ŷ - p(p·ŷ)` が縮退するので、`|p·ŷ| > 0.999` のときは
直前フレームの `north` を保持してロールを凍結する（極を通過しても絵が回らない）。

### 5.2 ズームと自動フレーミング

基準画角は §1b.3 の「プレイ窓 10.60° × 18.55°」。縦長の元ゲームと同じアスペクトを保つ。

| 段 | 可視角半径 | km/px @800px | 使う場面 |
| --- | ---: | ---: | --- |
| WORLD | 90°（地球全体） | — | タイトル、ゲームオーバー後の引き |
| **PLAY** | **9.28°**（＝プレイ窓の縦半分） | 2.58 | **通常プレイ。元ゲームと同一の画角** |
| FLOOR | 4.64°（＝PLAY の半分） | 1.29 | 自動フレーミングの寄り限界 |

**自動フレーミング**: プレイヤーと「最も危険な台風」（＝`(角距離 - 0.55r) / 速度` が最小の個体）の
角距離 Δ を毎フレーム求め、両方が入る最小の可視角半径
`clamp(Δ + 0.55r + 余白, FLOOR, PLAY)` へスプリングで寄せる。
→ 台風が遠い時は 9.28°（元ゲームと同じ引き）、迫ると自然に寄る。
**引きすぎない上限を PLAY に固定する**のが要点。元より広く見えると難度が下がって別ゲームになる。

`K_TW = 1.0`（実寸）を選んだので、元ゲームと同じ画角でも**見える範囲は 1179 × 2063 km**
（`K_TW = 1.6` なら 1886 × 3300 km）。地球全体に対して相対的に狭くなり、
「地球儀の上を移動している」感覚が強くなる。地図解像度を 10m にした理由でもある（§3.3）。

タイトル→開始時だけ WORLD → PLAY を 3 秒の slerp で繋ぐ手動演出を入れる。

### 5.3 酔い対策

- カメラの角速度に上限を掛ける
- **ロール（バンク）は入れない**。§5.1 の通り常に北が上
- 速度に応じた画角変化などの「速度演出」はしない
- ゲームオーバーのスローモーション（`dt *= 0.3`, 1500 ms）中もカメラは等速で追従する

## 6. 入力（**確定** — 元の操作系をそのまま移植）

元ゲームの操作は「**速度ベクトルの直接指定**」であり、旋回や加速度はない。維持する。

| 操作 | 元 | 本作 |
| --- | --- | --- |
| タッチ | ティッカー/ポップアップ/メニュー以外の**任意の場所**を押すと、そこに仮想スティック（半径44px）が出現。`(vx,vy) = clamp(drag)/44` | 同一 |
| キーボード | WASD / 矢印。`vx,vy ∈ {-1,0,1}` の生値 | 同一 |
| 速度 | `jp += (vx,vy) * M*0.125 * dt` | `(vx,vy)` を**接平面上の (東, 南) 成分**として解釈し、§2.3 の大圏ステップで進める |

「斜め入力が √2 倍速い」という元の性質は**バグではなく仕様として残す**
（キーボードとスティックで最大速度が変わってしまうが、元がそうなっている）。

`(vx, vy)` → 接平面ベクトル: `dir = east * vx + north * (-vy)`（画面下方向が南）。
`east = ŷ × p` を正規化、`north = p × east`。極では §5.1 と同じ縮退処理。

既存リポジトリと同じく、同一ビルドが `@media (pointer: coarse)` でタッチUIへ切り替わる。

### 実装して分かった、設計書が間違っていたこと

いずれも**面積・角度の機械的な検算**で見つけた。目視では気付けなかった。

1. **南極の扇形分割（旧 §3.3b）は使えなかった** — 面積が 2.39 倍になる。
   海岸線が極から見て星形でないため三角形が海側へはみ出して重なる。
   「極で切り開く」方式に差し替えた。→ 面積比 1.002
2. **earcut の長い三角形が球の内側へ沈む** — 最長弦 弧 60 度・沈み込み 924 km。
   red-green 細分を追加（§3.3b-2）。
3. **外接角半径の計算にリングの閉じ点が混ざっていた** — 日本 110m で 1.3% 小さく出て、
   換算定数 A が 0.026882 → 0.026501 に変わった。§1b の表を全面再計算。
4. **押しのけ判定が毎フレーム 6.7 ms かかっていた** — リングを配列の配列のまま走ると
   最大 83,725 辺のポインタ追跡で間に合わない。辺を型付き配列へ平らに並べ、
   姿勢の逆クォータニオンと重心をキャッシュして 2.78 ms にした。
5. **自前シェーダの出力に sRGB 変換が抜けていた** — 海の `#1B2F5E` がほぼ黒で出た。
   `#include <colorspace_fragment>` を追加。
6. **ティッカーの行が挿入直後に消えた** — CSS の `animation` は既定 duration が 0s なので、
   幅を測っている間に animationend が飛ぶ。アニメーションを貼り直し、削除は setTimeout に。
7. **カメラがタイトルで PLAY 画角に丸められていた** — 上限を WORLD に直し、
   「プレイ中は PLAY より引かない」制約は呼び出し側へ移した。
8. **`render/hud.js` が `rules/names.js` を import していた** — §0.3 の層違反。
   `layering` テストが検出。文言は呼び出し側から渡す形に直した。
